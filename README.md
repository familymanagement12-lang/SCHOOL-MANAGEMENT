# The McCarthy Hill School Management System + Library

A single-school React/Vite + Node.js/Express + PostgreSQL system. Existing modules are retained: dashboard, students, classes and subjects, attendance, results/report cards, timetable, fees and finance, staff registry, payroll, inventory, announcements, user accounts, settings and notifications. The Library adds a searchable catalogue, copy counts, unique book/barcode codes, student/staff borrowing, due dates, return tracking and overdue reporting. Fines are disabled.

## Requirements
- Node.js 18+ (20 LTS recommended)
- PostgreSQL 14+ (local PostgreSQL is supported; Docker is not required)

## Setup
1. Create a fresh database named `mccarthy_hill_school` in PostgreSQL/pgAdmin.
2. Copy `backend/.env.example` to `backend/.env`; set the migration/admin `DATABASE_URL`, a long random `JWT_SECRET` (at least 32 characters), `CORS_ORIGIN`, `ADMIN_EMAIL`, and a strong `ADMIN_PASSWORD` (12+ characters). After applying the schema, configure `APP_DATABASE_URL` to use a dedicated non-superuser runtime login without `BYPASSRLS`; the API refuses to run with an RLS-bypassing database role. Do not share or commit `.env`.
3. From the project root, run `npm install`, `npm --prefix backend install`, and `npm --prefix frontend install`. Then run `npm run db:init` to apply `sql/schema.sql` and all migrations, and `npm run admin:seed` to create/reset the initial administrator using the environment credentials. Class names are required, but class-teacher assignments and year levels are optional and can be added later.
4. Start the API with `npm run dev:backend` and the frontend with `npm run dev:frontend`. Frontend: `http://localhost:3000`; API: `http://localhost:5000`.
5. Sign in with the `ADMIN_EMAIL` and `ADMIN_PASSWORD` you configured. Change credentials securely after initial setup.

## Render deployment with Neon
`render.yaml` defines the Render Node API and static frontend services. Connect the project repository to Render and create a Blueprint from that file. Keep Neon as the PostgreSQL provider; do not use a local `.env` file as the production environment.

Before deploying, initialize the intended Neon database once from a trusted local machine using its owner connection in `backend/.env`: run `npm run db:init`, then `npm run admin:seed` with a strong, unique `ADMIN_PASSWORD`. These commands create the schema/migrations and the initial administrator; do not put the seed command in an automatic deploy/build step. Create a separate Neon runtime login with no superuser or `BYPASSRLS` privilege and the required table/sequence grants. Set the owner connection as `DATABASE_URL` and the restricted login as `APP_DATABASE_URL` in the Render API service. The API refuses to start in production without `APP_DATABASE_URL` and verifies that the runtime login cannot bypass RLS.

In the Render API service, set `CORS_ORIGIN` and `FRONTEND_URL` to the deployed frontend origin. In the static frontend service, set `VITE_API_URL` to the API service URL ending in `/api`, then redeploy the frontend so the build picks it up. Set secrets in Render's environment settings only; never commit them or paste them into chat. Use a unique production `JWT_SECRET` generated by Render. Verify login, finance/RLS access, and backups before sharing the public URL.

## Scripts
- `npm run db:init` applies the schema and all timetable migrations.
- `npm run db:migrate:class-assessments` applies the 50/50 class assessment grading migration independently.
- `npm run db:migrate:curriculum` adds curriculum pathways, subject mappings, and curriculum grading-configuration storage without deleting existing records.
- `npm run db:migrate:student-portal` adds result publication controls and student portal audit logging without deleting existing records.
- `npm run db:migrate:school-name` updates the school record to its correct name without deleting existing records.
- `npm run db:migrate:optional-class-year` allows classes to be created without a year level while preserving existing class assignments.
- `npm run db:migrate:optional-class-teacher` allows classes to be created before assigning a teacher while preserving existing class assignments.
- `npm run db:migrate:school-store` additively upgrades the existing inventory catalogue with suppliers, purchase receipts, stock movements, issuances, assets, requests, stocktakes, audit history, and row-level security.
- `npm run db:migrate:accountant-rls` adds the accountant finance role support, finance change audit history, and PostgreSQL row-level policies to finance tables.
- `npm run db:migrate:timetable` applies or rechecks the timetable-management migrations independently.
- `npm run admin:seed` creates the initial administrator; it does not print the password.
- `npm run dev:backend` starts the API.
- `npm run dev:frontend` starts Vite.
- `npm run build` builds the frontend.
- `npm run check:backend` checks backend JavaScript syntax.

## Single-school configuration
Public registration and subscription/plan routes are disabled; the seed process creates one fixed school record for The McCarthy Hill School, and the fresh-install schema enforces a single row in `schools`. Internal `school_id` columns remain in the existing database schema because the existing modules use them for referential integrity and scoped queries; they are not exposed as a school selector or tenant-creation feature. Use a fresh database for this fresh-data package.

## Library
Administrators and librarians can manage `/library`: add and edit books, search by title/author/code/ISBN/category, print barcode labels, issue books to existing student or staff records, and mark returns. A USB barcode scanner that types into the focused field (keyboard-wedge mode) works without a special driver; configure it to send Enter after each scan. When adding a title, scan an ISBN into the book-code field to look up and fill the title, author, publisher, and ISBN; review the details before saving. ISBN lookups use Open Library and require an internet connection. Non-ISBN barcode codes can still be entered manually. In Circulation, scan a book code or ISBN to select it for issue, then choose the borrower and due date. Scan a borrowed book code or ISBN in the return field to return its active loan; if multiple borrowers have the title, choose the correct borrower. Teachers can search the catalogue and view only their own borrowing history; they cannot view the school-wide register or issue/return books. Overdue items are flagged but no fines are calculated. Create librarian accounts in Accounts & Roles using the `librarian` role.

## School inventory
The existing inventory catalogue is extended in place; the additive `npm run db:migrate:school-store` migration preserves existing catalogue rows. Consumables use quantity-based stock, while reusable assets are registered individually and retain assignment, condition, maintenance, missing, and disposal history. Purchases increase stock only when a delivery is received; issuance, adjustments, and stocktake reconciliation are recorded as stock movements and cannot create negative stock.

Administrators, inventory users, and the separate `storekeeper` role can access the store dashboard, catalogue, suppliers, purchases, issuance, asset management, maintenance, stocktakes, alerts, reports, and transaction history. Only administrators can create accounts or dispose of assets. Teachers can submit and track their own departmental requests; approval and fulfilment are restricted to store roles on the backend. Create inventory or storekeeper accounts in Accounts & Roles. The legacy `store` role remains an alias for `inventory`.

Item and asset barcode labels can be printed. USB barcode scanners that type into the focused search field work in keyboard-wedge mode; configure the scanner to send Enter after each scan. Teachers can still view only inventory assigned to their account.

## Staff registry
The Staff Registry role selector includes common school job titles across teaching, administration, finance, library, inventory, IT, health, support, and operations, plus an `Other` option for custom titles. These are employee job titles used for staff records and payroll, not application login permissions.

## Results and grading
Class assessments are worth 50 points and the final exam is worth 50 points. Teachers select a class, subject, and term, add each term exercise and a mid-semester assessment with its maximum mark, then enter marks for the class. The system pools earned and possible marks across all class assessments and scales the percentage to 50. Teachers enter the final exam mark separately, out of 50. Apply this grading migration on an existing database with `npm run db:migrate:class-assessments`; `npm run db:init` includes it for a fresh database.

## Curriculum pathways
Years 1–6 use the common curriculum. Years 7–9 require a GES or Pearson class stream, and students inherit that stream when enrolled. Years 10–11 are automatically assigned to Pearson. Subject records can be mapped to one or more pathways; timetable teacher assignments and weekly requirements must use a subject mapped to the class pathway. On an existing database, run `npm run db:migrate:curriculum`; the migration preserves records and marks legacy Years 7–9 classes without known pathways as `UNASSIGNED` rather than guessing. Assign those classes a pathway before adding students or academic assignments. The grading-configuration table is provided for future curriculum-specific grading workflows; existing 50/50 report-card behavior remains unchanged.

## Student portal
Student accounts are created with student records and can sign in using the six-digit student ID or account email. Administrators can activate/deactivate accounts and reset a password from the Students page; temporary credentials are displayed once and require a password change. The `/student` portal uses student-only APIs that derive identity from the authenticated account, show only that student's profile/attendance/published results, and filter subjects, timetable and announcements to their assigned class/curriculum. Staff must publish results from Results before students can view them; editing published marks automatically unpublishes them. Apply the additive migration on an existing database with `npm run db:migrate:student-portal`. Assignments, learning-material uploads, exam calendars, profile photos and student self-service email reset are not currently supported by the existing application; the portal labels those sections unavailable rather than showing demo content.

## Accountant, finance audit, and PostgreSQL RLS
Administrators can create an `accountant` account from Accounts & Roles. Accountants have access to fee workflows, transactions, payroll, the finance overview, and the finance audit trail; they do not have access to school administration, academic, inventory, library, or user-management areas. Finance API routes enforce role checks independently of the frontend.

Run `npm run db:migrate:accountant-rls` on an existing database (or `npm run db:init` for a fresh database). The additive migration enables and forces school-scoped PostgreSQL RLS for fees, transactions, fee structures and items, student fee accounts, payroll, payroll deductions, and employee reads. Employee writes remain administrator-only. Database session context is populated from the verified JWT on each authenticated request and cleared before a pooled connection is reused. Finance row inserts, updates, and deletes are recorded in `finance_audit_log`; finance audit entries are readable but not mutable through the application roles.

RLS is a database-side safety boundary, not a replacement for API authorization. Keep `DATABASE_URL` for schema migrations and administration; use `APP_DATABASE_URL` for the runtime API connection. Give the app login `CONNECT` on the database, `USAGE` on `public`, DML privileges (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) on application tables, and sequence `USAGE`/`SELECT`; grant matching default privileges for tables and sequences created by the migration owner. Do not grant the runtime role `TRUNCATE`, schema creation, superuser, or `BYPASSRLS`. The runtime startup check rejects superuser and `BYPASSRLS` connections, and the audit table is not directly writable by the runtime role.

## Security/configuration notes
- No secrets or database credentials are included in this ZIP.
- `backend/.env` is intentionally excluded.
- `node_modules`, build output and `.git` metadata are excluded; install dependencies locally.
- API routes use bearer-token authentication and role checks; CORS defaults to the local Vite origin and can be configured with `CORS_ORIGIN`; library management is limited to admin/librarian/store, while teachers have catalogue and personal-loan read access. Password hashing uses bcrypt. Keep `JWT_SECRET` private and use HTTPS in any hosted environment.
- Review the existing password-reset email provider configuration before enabling password-reset email in production.

## McCarthy AI
- Visit `/ai` after signing in. The assistant is read-only and uses predefined, parameterized queries for verified school records; it does not execute model-generated SQL or change school data.
- Configure `OPENAI_API_KEY` in `backend/.env` and optionally set `OPENAI_MODEL` (defaults to `gpt-6.1-sol`) to enable generated summaries and teaching drafts. The key stays on the server. The OpenAI Responses API is used for text generation. [OpenAI text-generation guide](https://developers.openai.com/api/docs/guides/text) [API key security guidance](https://developers.openai.com/api/reference/overview)
- Without a key, supported factual questions still query authorized database records, but return a direct data response instead of an AI-written summary. Generated lesson plans, quizzes, and drafting are unavailable until configured.
- Requests are limited to 10 per authenticated user per minute, questions to 2,000 characters, and model output to 800 tokens. Database answers are scoped by role: administrators have school-wide access; teachers are limited to assigned classes; parents and students to linked accounts; librarians to circulation; storekeepers to inventory.
- Conversation history stays in browser memory and is sent to the backend with each request. The server sends only scoped aggregate records or catalog metadata to OpenAI, with storage disabled on the API request. AI is not used to make or apply changes.
- No database migration or extra package is required. Add the two AI variables to `backend/.env` and restart the backend. API usage is billed by the configured OpenAI project and varies with prompt and response size.
