# The McCarthy Hill School Management System + Library

A single-school React/Vite + Node.js/Express + PostgreSQL system. Existing modules are retained: dashboard, students, classes and subjects, attendance, results/report cards, timetable, fees and finance, staff registry, payroll, inventory, announcements, user accounts, settings and notifications. The Library adds a searchable catalogue, copy counts, unique book/barcode codes, student/staff borrowing, due dates, return tracking and overdue reporting. Fines are disabled.

## Requirements
- Node.js 18+ (20 LTS recommended)
- PostgreSQL 14+ (local PostgreSQL is supported; Docker is not required)

## Setup
1. Create a fresh database named `mccarthy_hill_school` in PostgreSQL/pgAdmin.
2. Copy `backend/.env.example` to `backend/.env`. The API uses only `APP_DATABASE_URL`, a restricted runtime login. Database-changing CLI commands use only `DATABASE_URL_UNPOOLED`, require the pinned development identity and migration owner, verify the live database/current/session roles, and serialize through the shared advisory lock. They never fall back to `DATABASE_URL` or `APP_DATABASE_URL`. For an intentionally local PostgreSQL database, explicitly set `MIGRATION_TARGET=local`, `MIGRATION_ROLE` to its schema owner, and use a loopback `DATABASE_URL_UNPOOLED` targeting `mccarthy_hill_school`; local mode cannot target a network host. Set a long random `JWT_SECRET` (at least 32 characters), `CORS_ORIGIN`, `ADMIN_EMAIL`, and a strong `ADMIN_PASSWORD` (12+ characters). Do not share or commit `.env`.
3. From the project root, run `npm install`, `npm --prefix backend install`, and `npm --prefix frontend install`. Run `npm run db:init` for general application tables, then `npm run db:migrate:timetable` for the protected class, curriculum, and timetable sequence, `npm run db:migrate:learning-assignments` for assignments, and `npm run db:migrate:learning-platform` for assignment row authorization and Learning Materials. Neon commands accept only the pinned development branch; production requires a separately reviewed release process. Class sections and curricula must be explicitly classified before subject or timetable allocation.
4. Start the API with `npm run dev:backend` and the frontend with `npm run dev:frontend`. Frontend: `http://localhost:3000`; API: `http://localhost:5000`.
5. Sign in with the `ADMIN_EMAIL` and `ADMIN_PASSWORD` you configured. Change credentials securely after initial setup.

## Render deployment with Neon
`render.yaml` defines the Render Node API and static frontend services. Connect the project repository to Render and create a Blueprint from that file. Keep Neon as the PostgreSQL provider; do not use a local `.env` file as the production environment.

Do not run the development-only initialization or migration commands against production. Production schema changes require a separately reviewed and approved process; the protected timetable runner accepts only the pinned development branch. Create a separate Neon runtime login with no superuser, `BYPASSRLS`, database-creation, role-creation, schema ownership, or migration-owner membership privileges. Set that restricted login as `APP_DATABASE_URL` in the API environment; the API never falls back to the migration `DATABASE_URL` and verifies the connected role before listening.

In the Render API service, set `CORS_ORIGIN` and `FRONTEND_URL` to the deployed frontend origin. In the static frontend service, set `VITE_API_URL` to the API service URL ending in `/api`, then redeploy the frontend so the build picks it up. Set secrets in Render's environment settings only; never commit them or paste them into chat. Use a unique production `JWT_SECRET` generated by Render. Verify login, finance/RLS access, and backups before sharing the public URL.

Student-portal setup is separate because its historical migration contains a result backfill.

- `npm run db:migrate:fee-overrides-staff-attendance` adds individual fee adjustments and the staff attendance register without removing existing fee or employee data.
- `npm run db:migrate:accountant-rls` adds the accountant finance role support, finance change audit history, and PostgreSQL row-level policies to finance tables.
- `npm run db:migrate:feeding` applies the additive compulsory-feeding, rate/calendar, account, receipt, allocation, refund, ledger, and audit schema using a direct (unpooled) database connection.
- `npm run db:migrate:feeding-officer-audit-edit` adds audit history for feeding account/frequency changes and officer-scoped audit reads for Feeding, Market, and Tuckshop activity.
- `npm run db:migrate:parent-portal` adds parent access audit/preferences/enquiries and read-only, linked-child RLS policies for fees, fee structures, and feeding payment records.
- `npm run db:migrate:curriculum-transition` is a compatibility alias for the complete, verified timetable/curriculum migration sequence.

It requires the pinned development branch's direct connection, records each migration in `app_schema_migrations` under the shared advisory lock, and stops when legacy objects exist without matching ledger history. - `npm run db:migrate:learning-platform` adds role-scoped assignment RLS, explicit runtime grants, and Learning Materials tables/policies. It requires the assignment migration to be recorded, refuses untracked or drifted schema, and verifies recorded postconditions before skipping.
- The assignment authorization and Learning Materials migrations use the `20261127` date. Their earlier `20261129` names were future-dated relative to the remediation date without a scheduled-release reason; identifiers, SQL ledger values, runner references, and tests were corrected together. Each command now runs under the same approved-target identity and role checks, shared advisory lock, and transaction. Most legacy general migrations still lack runner-level ledger entries and definition-level postconditions, so their repeatability must be reviewed before re-execution. The student-portal command refuses historical result backfills when result rows exist, refuses partial or legacy schema drift, and skips only after it verifies the insert-only snapshot trigger. Curriculum/optional-class aliases still invoke the complete protected timetable runner; no standalone path applies protected DDL.

- `npm run dev:frontend` starts Vite.

Assignment and Learning Materials uploads require a private S3-compatible bucket. `infra/learning-files-bucket.yaml` creates an AWS bucket with all public access blocked, bucket-owner object ownership, default encryption, versioning, and a TLS-only bucket policy. Configure `LEARNING_FILES_BUCKET`, `AWS_REGION`, and a scoped storage identity through the host IAM role or AWS SDK credentials (`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, plus `AWS_SESSION_TOKEN` for temporary credentials). Uploads accept at most five files per request and 10 MB per file, with matching file signatures for PDF, DOC, DOCX, JPG/JPEG, and PNG. Objects are private and served only through authenticated downloads with `private, no-store` headers; there are no public URLs. Without bucket configuration, file operations fail with a service-unavailable response.

## Single-school configuration
Public registration and subscription/plan routes are disabled; the seed process creates one fixed school record for The McCarthy Hill School, and the fresh-install schema enforces a single row in `schools`. Internal `school_id` columns remain in the existing database schema because the existing modules use them for referential integrity and scoped queries; they are not exposed as a school selector or tenant-creation feature. Use a fresh database for this fresh-data package.

## Library
Administrators and librarians can manage `/library`: add and edit books, search by title/author/code/ISBN/category, print barcode labels, issue books to existing student or staff records, and mark returns. A USB barcode scanner that types into the focused field (keyboard-wedge mode) works without a special driver; configure it to send Enter after each scan. When adding a title, scan an ISBN into the book-code field to look up and fill the title, author, publisher, and ISBN; review the details before saving. ISBN lookups use Open Library and require an internet connection. Non-ISBN barcode codes can still be entered manually. In Circulation, scan a book code or ISBN to select it for issue, then choose the borrower and due date. Scan a borrowed book code or ISBN in the return field to return its active loan; if multiple borrowers have the title, choose the correct borrower. Teachers can search the catalogue and view only their own borrowing history; they cannot view the school-wide register or issue/return books. Overdue items are flagged but no fines are calculated. Create librarian accounts in Accounts & Roles using the `librarian` role.

## School inventory
The existing inventory catalogue is extended in place; the additive `npm run db:migrate:school-store` migration preserves existing catalogue rows. Consumables use quantity-based stock, while reusable assets are registered individually and retain assignment, condition, maintenance, missing, and disposal history. Purchases increase stock only when a delivery is received; issuance, adjustments, and stocktake reconciliation are recorded as stock movements and cannot create negative stock.

Administrators, inventory users, and the separate `storekeeper` role can access the store dashboard, catalogue, suppliers, purchases, issuance, asset management, maintenance, stocktakes, alerts, reports, and transaction history. Only administrators can create accounts or dispose of assets. Teachers can submit and track their own departmental requests; approval and fulfilment are restricted to store roles on the backend. Create inventory or storekeeper accounts in Accounts & Roles. The legacy `store` role remains an alias for `inventory`.

Item and asset barcode labels can be printed. USB barcode scanners that type into the focused search field work in keyboard-wedge mode; configure the scanner to send Enter after each scan. Teachers can still view only inventory assigned to their account.

## Kitchen and weekly operations
The `/operations` workspace reuses the inventory catalogue, suppliers, purchase receipts, stock movements, and audit log. Kitchen plans are estimates only: they do not create stock or expenses. Link a planned item to a purchase line to compare its estimates with received quantities and actual receipt costs. New inventory purchases require administrator approval before delivery can be received; existing orders are preserved as approved.

Administrators, accountants, and feeding/tuckshop officers can record weekly Tuckshop & Purchases and Feeding & Marketing entries; officers may also view kitchen plans. Both registers group entries into calendar weeks, allow multiple revenue or expense entries per date, retain expense descriptions, support date/month/term filters, and export Excel or print. These entries are kept separate from POS sales, school-fee transactions, and the completed Lunch Register allocations. This checkout has a student workbook uploader, but no dedicated Tuckshop POS or operations workbook-import centre was found during the audit.

## Fees and staff attendance
When applying a fee structure to selected classes, administrators and accountants can set a different total fee for an individual student and must record a reason for each difference. Students without an adjustment receive the normal class total. The adjustment and reason are retained with the fee record and finance audit history.

Administrators can switch the Attendance page to the staff register, mark active employees present, absent, late, or excused for a selected date, and record a required reason for each absence. Staff attendance changes are retained in an audit history and are protected by backend authorization and school-level row security. Apply the additive migration with `npm run db:migrate:fee-overrides-staff-attendance`.

## Lunch Register and Feeding
The `/feeding` workspace automatically creates a feeding account for each existing and newly added student. Configure non-overlapping academic terms, scheduled weekdays, class-specific daily rates, and approved holidays, vacations, or additional school days. Rate changes require a future effective date; historical obligation snapshots and allocated receipts are preserved. Daily, weekly, monthly, and termly payment frequencies are stored with effective-dated history.

Administrators, accountants, and the Feeding Officer can use the authorized register and feeding-payment workflows. Administrators manage rates and the feeding calendar; administrators/accountants manage accounts, frequencies, financial reports, receipts, and refunds. The Feeding Officer can record feeding-only payments and daily serving coverage, but cannot post tuition or access combined financial reports. Assign the `Feeding Officer` role through Accounts & Roles.

The Fees page records offline cashier payments for school fees only, feeding only, or both. Combined receipts allocate school-fee components to the existing School Fees transaction ledger and feeding components to a separate Feeding operational ledger. School-fee receipts cannot exceed billed balances; feeding payments may be partial or create advance credit. Refunds reverse the original component allocations. No online payment gateway or parent-initiated payment is configured. Excel exports are available for daily, weekly, monthly, termly, class-collection, outstanding-balance, advance-credit, and payment-history reports.

For an existing database, apply `npm run db:migrate:feeding` using only the approved direct connection in `DATABASE_URL_UNPOOLED`; `DATABASE_URL` is never a migration fallback. `npm run db:init` includes this additive migration for a fresh database. Configure terms, weekday schedules, class rates, and calendar exceptions in `/feeding` before recording feeding payments. No production migration is applied automatically.

## Staff registry
The Staff Registry role selector includes common school job titles across teaching, administration, finance, library, inventory, IT, health, support, and operations, plus an `Other` option for custom titles. These are employee job titles used for staff records and payroll, not application login permissions.

## Results and grading
Class assessments are worth 50 points and the final exam is worth 50 points. Teachers select a class, subject, and term, add each term exercise and a mid-semester assessment with its maximum mark, then enter marks for the class. The system pools earned and possible marks across all class assessments and scales the percentage to 50. Teachers enter the final exam mark separately, out of 50. Apply this grading migration on an existing database with `npm run db:migrate:class-assessments`; `npm run db:init` includes it for a fresh database.

## Curriculum pathways
Class education section, year label/level, curriculum, teaching model, class teacher, and other programme are separate attributes. Early Years, Primary, JHS, Other programmes, and pending classifications are represented explicitly. Class names and numeric levels do not infer a school section or curriculum; Year 7–10 remain pending until an administrator confirms their mapping. Primary classes retain a class teacher, Years 1–3 use the class-teacher model, and Year 4 can use either model for the transition. Subject applicability lists the education sections and optional numeric levels explicitly. Subject and timetable allocations are blocked while a class section or curriculum is unassigned. Class configuration and student class changes require a reason and are recorded; legacy result and class-history context is not fabricated from current records and is shown as unrecorded when absent.

## Student portal
Student accounts are created with student records and can sign in using the six-digit student ID or account email. Administrators can activate/deactivate accounts and reset a password from the Students page; temporary credentials are displayed once and require a password change. The `/student` portal uses student-only APIs that derive identity from the authenticated account, show only that student's profile/attendance/published results, and filter subjects, timetable and announcements to their assigned class/curriculum. Staff publish assignments and class resources; students can submit work and see returned feedback, or download class Learning Materials from authenticated private storage. Staff must publish results from Results before students can view them; editing published marks automatically unpublishes them. Exam calendars, profile photos and student self-service email reset remain unavailable.

The student-portal migration includes a historical result backfill. Its runner refuses to apply it when result rows already exist, refuses partial or legacy portal schema states, and never reruns it over the insert-only snapshot trigger. On a fresh database, run it before the protected timetable sequence and before creating results. `db:init` intentionally leaves this migration out.

Parent accounts are created and linked only by administrators from **Parent accounts**. The parent portal uses existing `parents`/`student_parent` links, school fee invoices and receipt allocations, feeding obligations/allocations, attendance, published results, published timetables, announcements, and user notifications. Parents can switch among approved children, view/print receipts and download CSV statements, update their own contact details and notification preferences, and send an enquiry or child-information correction request for staff review. Parents cannot edit student, fee, feeding, attendance, or academic records or submit payment declarations. Year 6 families can submit a GES or Pearson pathway request from **Curriculum selection**; administrators review it and separately assign the matching class from **Curriculum selections**. Parent requests never assign class sections or promote students automatically. Parent credentials are issued/reissued by an administrator and displayed once; they must be changed at first login. Email/phone login uses the parent account's email or registered parent phone. Existing databases must apply `npm run db:migrate:parent-portal` after the fee, feeding, and student-portal migrations, then `npm run db:migrate:curriculum-transition`, using only the pinned development branch's direct `DATABASE_URL_UNPOOLED`; pooled endpoints and `DATABASE_URL` fallback are rejected. Homework, school event/exam calendars, teacher messaging, published report-card comments, and email delivery of parent invitations are not connected in the existing system; the portal does not fabricate those records.

## Accountant, finance audit, and PostgreSQL RLS
Administrators can create an `accountant` account from Accounts & Roles. Accountants have access to fee workflows, transactions, payroll, the finance overview, and the finance audit trail; they do not have access to school administration, academic, inventory, library, or user-management areas. Finance API routes enforce role checks independently of the frontend.

Run `npm run db:migrate:accountant-rls` on an existing database (or `npm run db:init` for a fresh database). The additive migration enables and forces school-scoped PostgreSQL RLS for fees, transactions, fee structures and items, student fee accounts, payroll, payroll deductions, and employee reads. Employee writes remain administrator-only. Database session context is populated from the verified JWT on each authenticated request and cleared before a pooled connection is reused. Finance row inserts, updates, and deletes are recorded in `finance_audit_log`; finance audit entries are readable but not mutable through the application roles.

RLS is a database-side safety boundary, not a replacement for API authorization. Use `APP_DATABASE_URL` only for the runtime API connection and `DATABASE_URL_UNPOOLED` only for reviewed CLI migration commands. The runtime role needs `CONNECT` on the database, `USAGE` on `public`, DML privileges (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) on application tables, and sequence `USAGE`/`SELECT`; grant matching default privileges for tables and sequences created by the migration owner. Do not grant the runtime role `TRUNCATE`, schema creation, superuser, or `BYPASSRLS`. The runtime startup check rejects superuser and `BYPASSRLS` connections, and the audit table is not directly writable by the runtime role.

## Security/configuration notes
- No secrets or database credentials are included in this ZIP.
- `backend/.env` is intentionally excluded.
- `node_modules`, build output and `.git` metadata are excluded; install dependencies locally.
- API routes use bearer-token authentication and role checks; CORS defaults to the local Vite origin and can be configured with `CORS_ORIGIN`; library management is limited to admin/librarian/store, while teachers have catalogue and personal-loan read access. Password hashing uses bcrypt. Keep `JWT_SECRET` private and use HTTPS in any hosted environment.
- Review the existing password-reset email provider configuration before enabling password-reset email in production.

## McCarthy AI
- Visit `/ai` after signing in. **General AI** prepares educational material, while **School Data** answers only with predefined, authorized school-record queries. The model cannot run SQL or change school records.
- Copy `backend/.env.example` to `backend/.env`, then set `OPENAI_API_KEY` to a newly created key and optionally set `OPENAI_MODEL` (defaults to `gpt-4.1-mini`). Never put this key in frontend variables, source files, commits, or chat. If a key has been shared, revoke it and create a replacement. The backend uses the official OpenAI Node SDK and Responses API with storage disabled.
- For an existing database, run `npm run db:migrate:ai-assistant` once using the owner/migration connection in `backend/.env`; fresh databases receive this migration through `npm run db:init`. Set the same `OPENAI_API_KEY` in the Render API service's secret environment variables; never set it on the static frontend. No deployment or migration is run automatically.
- Without a configured key, authorized School Data questions still return a plain-language answer from available records. General AI and learning-material generation clearly report that the service is not configured; no fake AI answers are shown.
- Conversations are saved per account, separated by mode, and automatically removed after 30 days by default. Names, contact details, and long numeric identifiers are masked before storage or sending prompts to OpenAI. Users can delete their own conversations. API requests are limited to 10 per user per minute across backend instances, question text to 4,000 characters, and generated output to 1,200 tokens by default.
- Database permissions stay on the backend: administrators can ask school-wide questions; teachers are limited to assigned classes; librarians to library topics; inventory and storekeeper roles to inventory. AI usage summaries are available to administrators only. Request model/token usage is recorded without prompts; configure both `AI_INPUT_COST_PER_MILLION_USD` and `AI_OUTPUT_COST_PER_MILLION_USD` to enable cost estimates.
- Optional backend controls are `AI_RATE_LIMIT_PER_MINUTE`, `AI_MAX_INPUT_CHARS`, `AI_MAX_OUTPUT_TOKENS`, `AI_REQUEST_TIMEOUT_MS`, and `AI_CONVERSATION_RETENTION_DAYS`. Restart the backend after changing local environment settings. AI usage is billed by the configured OpenAI project.
